# Audit against the evidence, 25 October 2026

This audit checks the repository's numbers and its test against the data and code they come from. It does not check what the sources say. Whether a vote tally, a date or a court's holding is right is a question for the sources, and that work is the adversarial review and issues 2, 4 and 11 to 15. Here the question is narrower: does each number the prose states match the file that is supposed to produce it, and can T1 come out either way?

The audit was run on commit 008e07f (59241d5 before the history rewrite recorded in change log item (ao)), the state of `main` on 25 October 2026.

## How it was done

1. **Every number listed.** Two readers who had not worked on the repository (language-model agents, as for the coding) listed every number a reader is asked to believe. One read the note and `research/coding-2026-10-22/results.md`. The other read the root README, `codebook/README.md`, the two research READMEs, the four research notes and every issue with its comments. Each number is classed as computed (it should follow from the repository's data), external (a fact the repository records from a source), or design (a rule fixed in advance). Their lists are merged in `audit-2026-10-25-provenance.csv`.
2. **Each computed number traced** to the file and field that produce it, and marked as matching, disagreeing, or without a source.
3. **Part of the trace turned into a script.** `analysis/check_numbers.py` recomputes, from the committed data, the numbers that can be recomputed directly: 75 checks, covering 123 of the listed numbers. It fails if the prose no longer says what the data gives. It was itself checked by planting a wrong number in a copy of the repository and a changed value in a copy of the data; it failed on both.
4. **The README's commands rerun** in a fresh clone.
5. **T1 checked for whether it can fail,** on the first run's configuration and on the largest unit the frame allows.

The readers listed 1,286 numbers:

| Class | Numbers | Status |
|---|---|---|
| Computed | 596 | 123 checked by the script; 338 traced by hand; 26 disagree with the data or are out of date; 101 dated records not re-verified; 8 in working notes not re-verified |
| External | 440 | Not checked here, except 14 that the repository's own files also record |
| Design | 250 | Rules fixed in advance, not measurements |

So 461 of the 596 computed numbers trace to the data, and all 26 that do not fall under the findings below. The 101 dated records are mostly process facts in the change log, the run report and the issue comments, such as how many readers ran or which round of reading a fix followed; no data file records them, so they rest on the record that states them.

## What holds up

- **Every rebuild reproduces the committed files.** In a fresh clone, `assemble.py` rebuilds `codebook/m4-codebook.csv` and `assemble_sample.py` rebuilds `codebook/comparison-sample.csv`, both identical byte for byte. `build_frame.py --draw` gives 130 rows, 14 challenged, 116 unchallenged and 39 sampled, and the rebuilt frame matches the committed one on every shared column of every row. `t1_revised.py detect 5 5 1 0`, `predict` and `kappa` print what the README and results.md say.
- **The counts in the prose match the data.** All 75 of the script's checks pass. They cover the frame's counts and decade table, both draws' composition and the shift between them, the comparison sample's coded values and agreement table, the codebook's row and adjudication counts, and the first run's configuration and verdict. The hand traces cover the rest of the current-state prose, including the merge-defect table, the same-page rule, both rounds of verification, the one-vote table and the worked example in the README, and they match.
- **T1 can fail, and can succeed.** On a configuration the full unit could reach (11 rows, 6 of them Adverse, 6 discordant split 3 and 3), the detectability check passes in both directions, at p = 0.043 at each extreme. The shuffle check on that configuration returns a rejection rate of 0.025 against the exact type-one rate of 0.022, within the 0.02 the protocol requires. So the must-fail control and the must-detect check both work when there is something to detect.
- **The first run's verdict is reproduced, and both reasons for it are recorded.** The first reason is the one the note gives: one discordant row against a minimum of six. The second is in the third addendum to results.md: once the 1994 row was recoded Adverse, every primary row was Adverse, so no permutation could change S and no result was possible even with six discordant rows. `detect 6 6 3 3` confirms the second reason: six discordant rows, all outcomes Adverse, p of 1.0 at both extremes.

## Findings

Ordered by what each costs. None changes a verdict. Findings 1, 2, 5, 7, 8 and 9 were corrected later the same day, as change log item (ap) records; the text below describes the repository as audited.

### Changes what a sentence means

**1. The comparison sample's README names the wrong side of the comparison.** It says of three sample rows that "the decision rule predicts Adverse and the Court's stated signs predict Not adverse." The Court's stated signs are the decision rule's inputs, so the sentence sets the rule against itself. In the data (`codebook/comparison-sample.csv`, rows 95, 106 and 111), the decision rule predicts Adverse and the elite-interest reading, which goes by direction, predicts Not adverse. The fix is to name the elite-interest reading.

**2. The README's Status section says the first run was inconclusive "before any outcome was looked at."** results.md and change log item (ab) say otherwise: the docket reader delivered outcomes with litigation timing, so the person assembling the table had seen the outcomes before the detectability check was computed. What is true is that the check was computed by code from N, K and the fixed predictions alone, so the outcomes could not change it. The sentence should say that.

### Weakens a claim or a plan

**3. On the full unit, T1 reaches its minimum only if every remaining codable row is discordant.** The primary analysis takes challenged Basic Laws judged after 1995 with an outcome of Adverse or Not adverse. On the frame's outcome classes, which are the challenge reader's and provisional until the docket reader codes each row under step 4, the frame has 11 such rows, and 2 more are pending. Five are coded: 1 discordant, 2 concordant, 2 undetermined. Of the other six, the 1992 Basic Law cannot be coded until a record names its voters, and none is known to. That leaves five codable rows: the 2023 Incapacity amendment and the four rows of issue 8 that have judgments (1999, 2010, 2016 and 2020). To reach six discordant rows, all five must be discordant.

Even then, whether the test can decide depends on how many of the ten rows are Adverse (K). Six of them already have Adverse outcomes, so K is at least 6; the rest depends on how the docket reader codes the four rows of issue 8 under step 4. With ten rows and six discordant, computed with `t1_revised.py detect`:
- K of 6, if all four issue 8 rows are Not adverse: only splits of the six of 1 and 5, 3 and 3, or 5 and 1 pass the detectability check.
- K of 7: only a split of 3 and 3 passes.
- K of 8 or more: nothing passes, because with nearly every row Adverse the permutations barely move S.

The two pending cases, once decided, would ease this a little. The note's outcome table already says what to do if the minimum fails on the full unit: widen the unit. The finding is that this result is likely before issue 8 is coded, not only after, and neither the note nor issue 8 says so. That bears on whether coding issue 8 is the next best use of effort. The same point touches the order of work: results.md and the note's outcome table put the comparison sample first among the work toward "the record T1 needs." For the primary test the sample adds nothing, as change log item (am) says; it serves step 14.

**4. The Incapacity amendment's coalition-only blank may be fillable from data the project already uses.** results.md says the Open Knesset vote tables "cover October 2003 to July 2021, so the 2023 rows need the Knesset's own site." But the redraw's vote extracts, from the same mirror, include named roll calls of 23 January 2023 and 29 October 2024 (`vote-extracts-redraw.json`). If the tables hold the vote of 23 March 2023, the blank can be coded from the record, as the protocol requires, and the row enters the primary analysis. The README's "First in the queue" section also says issue 6 gates "the two 2023 rows"; that may no longer be true for this one. The tables are not in the repository, so this is filed as an issue rather than settled here.

**5. The one-vote result is stated two ways.** The sample README counts 19 rows with a final vote found: on 18 the vote approved that law alone, and on the 1980 Jerusalem law what else the vote covered is not established. Change log item (am) and the issue 9 comment both say that on all 19 "each vote approved one law." The README's version is the accurate one.

**6. The frame's change counts have no script behind them, and recomputing them gives one fewer.** The frame README and change log item (al) give 141 Basic-Law changes through January 2023 for the corrected frame and 137 for the frame as built, counting each Basic Law a law amends once. No script in `analysis/` produces either figure. Recomputed under that rule, with a law that amends nothing counted once, the corrected frame gives 140 and the frame as built 136. The gap is one in both, which points to one row counted differently. The likely candidates are the three re-enactments, rows 36, 37 and 68 of the corrected frame, each of which both enacts a Basic Law and amends others. The comparison with the Court's 139 survives either way: 122 laws and 140 changes still bracket it. The figure should come from a script, with the rule for re-enactments written down.

### Costs attention only

**7. Passages written before the run's addenda still read as current.** Three addenda to results.md changed the run after it was written up. The situated beneficiary replaced the named beneficiary in F, and the 1994 row's outcome became Adverse. Several passages still show the earlier state without saying so:
- results.md's recoded table gives the 1994 row's outcome as Not adverse; its pre-outcome checks give K = 4 and p = 0.4; step 12's exploratory line gives N = 3 and K = 2; and its classification table gives Reasonableness F = 3.
- results.md's summary and the codebook README (its section on why the columns are what they are) say "the one row with all four signs" is the 2020 amendment. Under the situated sign, Reasonableness has all four too. The point they make survives, since the 2020 row is still the only one with all four signs and a Neutral direction.
- The codebook README says the Incapacity amendment "lost two of its signs" and "scores on two in the recoded table." That counts the named beneficiary. Under the situated sign it scores on three, with one blank.
- The first addendum names `circumstances.json` as the first circumstances reader's report. That file now holds the second reader's report; the first is `circumstances-ac.json`, as change log item (af) says.

The originals are dated records and should stay. Each wants a one-line pointer to the addendum or entry that supersedes it.

**8. Change log item (am) says the adjudicator settled "seven questions on situated_beneficiary."** The adjudication sheet put three interpretive questions, and the adjudicator's answers ruled on seven rows (`adjudications-redraw-all.json`). "Three questions, ruling on seven rows" is the accurate count. The change log is a dated record, so this is a correction to log, not an edit.

**9. Stale passages.**
- The frame README's "Counts and checks" section says the one-vote expectation "cannot be checked until the sampled rows are coded; it is carried forward." It has since been checked (change log (am)), as the section on the redraw says.
- The README's "First in the queue" lists the open verification issues "as of 22 October 2026" as 2, 4 and 7 to 15. Issue 7 was closed that afternoon, and the list leaves out issue 6, which carries the label too. It also says issue 6 gates the comparison sample, which has since been coded without it.
- The comment on issue 8 gives the frame as "122 rows, 14 challenged." That was the frame as built; the corrected frame has 130 rows (change log (al), issue 9).

**10. `t1_revised.py detect` stops with a Python error when given more discordant rows than rows,** instead of saying the input is impossible. It gives correct results on every possible input.

## A correction to the plan for this audit

The plan said to rerun T1's power check on the 39-row comparison sample. That was a mistake. The sample's outcome is Not challenged, so it enters only step 14's exploratory analysis of the challenge stage, never the primary test, and the detectability check does not apply to it. Change log item (am) already says the sample changes no T1 verdict. Step 14 states no test and no threshold, so it cannot fail. That is allowed for an analysis labelled exploratory, but it means the 39 coded rows can describe the challenge stage and cannot refute anything about it.

## What could not be checked

- **The 440 external numbers.** Vote tallies, dates, members' counts and counts reported by courts or scholars are only as good as their sources. Checking them against the sources is the adversarial review's work and that of issues 2, 4 and 11 to 15.
- **The 101 dated records and 8 working-note numbers,** for the reason given above.
- **Whether the inventory is complete.** Two readers working separately listed the numbers, and each checked by script that every quotation is an exact copy of its line. Neither list can show what it missed.
- **Finding 4's vote.** Whether the Open Knesset tables hold the 23 March 2023 roll call needs the tables, which are not in the repository.
- **Finding 6's original rule.** How the 141 and 137 were counted is not recorded, so which row accounts for the difference is a guess.

Two issues are proposed for what this audit could not settle:
- Code the Incapacity amendment's `coalition_only` cell from the Open Knesset vote tables, if they hold the 23 March 2023 roll call (finding 4).
- Compute the Basic-Law change counts by script, and write down how a re-enactment counts (finding 6).

Finding 3 bears on issue 8 and is proposed as a comment there rather than a new issue.
